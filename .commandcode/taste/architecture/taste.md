# architecture
- Think in systems rather than isolated features, prioritizing overall maintainability and minimal cognitive load. Confidence: 0.95
- Prefer a single Docker container deployment that bundles all services together under one roof. Confidence: 0.87
- Fix issues permanently at the source (Dockerfile, setup scripts, config) rather than applying temporary runtime patches to running containers. Confidence: 0.90
- WA_Automation UI is the primary customer-facing interface; OpenWA serves as the internal engine/API layer not directly exposed to users. Confidence: 0.80
- Before implementing major architectural changes, present the plan for user approval first and ask clarifying questions. Confidence: 1
- When client infrastructure has constraints outside their control (e.g., WAF blocking link previews), pragmatic workarounds like monkey-patching internal APIs are acceptable solutions rather than attempting to fix external limitations. Confidence: 0.85
- Use only React (no Django/Python) in the tech stack; use OpenWA's Bull MQ instead of Celery for task queuing. Confidence: 0.85
- Leverage OpenWA's built-in Redis and BullMQ instead of adding redundant separate services. Confidence: 0.65
- When dealing with undocumented features, explore iteratively (try, fail, refine) within the actual capabilities of the underlying OpenWA engine rather than hacking/patching around it. Confidence: 0.70
- Use multi-module fallback patterns when patching WhatsApp Web internals — try multiple module name candidates (e.g., `WAWebCollections`, `WACollections`, `Store`) and log which one succeeds, so the code adapts to WhatsApp Web's changing internal structure. Confidence: 0.85
- When upgrading a library (e.g., wwebjs) that has custom monkey-patch workarounds, audit those patches before deploying — verify field names, enum values, and module paths against the new version's source code. Field names in patches (`thumbnail`, `jpegThumbnail`) and enum values are version-specific and break silently if not updated. Confidence: 0.95
- Gracefully degrade optional features (e.g., link preview injection) — catch failures with try-catch, log warnings, and fall back to default behavior rather than throwing errors that could block the entire operation. Confidence: 0.90
- For ngrok in docker-compose, conditionally include `--url=${NGROK_URL:-}` in the command when NGROK_URL is set in .env. Confidence: 0.65
- For Render free tier services: do not configure persistent disks (unsupported on free plan). Confidence: 0.65
- For Render services with an attached disk: do not set maxShutdownDelaySeconds (not supported). Confidence: 0.65
- When the production database is missing a table or column (caught via deployment runtime errors), create a proper TypeORM migration file following the project's existing conventions, supporting both Postgres and SQLite — never enable `synchronize: true` or apply manual SQL patches to running containers. Confidence: 0.80
- When you need a count of records, add a dedicated count endpoint/query (e.g., `COUNT(*)`) rather than fetching all records and calling `.length` in JS — the latter is capped by pagination defaults and doesn't reflect the actual total. Confidence: 0.85
- Time-based entity transitions (e.g., completing an advt campaign once its last day fully elapses at midnight) must run on a scheduled job (NestJS `@Cron(EVERY_MINUTE)` in the scheduler service) rather than only on-read checks — a cron survives server restarts and fires with no page visits, while the on-read `checkExpired()` stays as a safety net. Confidence: 0.75
- In NestJS controllers, place static routes (e.g., `@Get('counts')`) ABOVE parameterized routes (`@Get(':id')`) — otherwise the parameter route matches first and swallows the static path. Confidence: 0.9
- Never hardcode presentation formatting (prefixes, separators, bullet styles, emoji) in backend/business logic or service layers. The template layer should fully control how data is rendered — pass raw data up and let the user-defined template decide the formatting. Confidence: 0.85
- Prefer strict, minimal precision over recall when extracting structured content from HTML. Only extract the first matching element of a repeating pattern (e.g., h3 headings) as bullet points. Extend to adjacent siblings only if they directly follow with no non-whitespace elements in between — never use `nextAll()` to grab all distant matches separated by other content. Confidence: 0.9
- WhatsApp's native link preview crawler runs on WhatsApp's own servers, not inside our browser session — CDP request interception can only serve cached HTML/images to requests originating from our browser; the user-visible preview is controlled by the monkey-patched `getLinkPreview` fallback that injects a pre-fetched base64 thumbnail when the native crawl returns an empty/undersized thumbnail. Confidence: 0.6
- WhatsApp Web renders a link preview as a full-width banner only when the `getLinkPreview` payload carries a real CDN-hosted thumbnail (`thumbnailDirectPath` plus `thumbnailSha256`/`thumbnailEncSha256` and dimensions) — an inline base64 `thumbnail` alone always renders as a compact card, regardless of dimensions. When native crawl fails, reproduce the CDN upload in-page through WA's own pipeline (`WAWebMediaOpaqueData.createFromData` → `WAWebPrepRawMedia.prepRawMedia` → `WAWebMediaStorage.getOrCreateMediaObject` → `WAWebMediaMmsV4Upload.uploadMedia`, mirroring wwebjs's processMediaData) and inject the media entry's fields; verify the exact proto field names by grepping the live runtime bundle, and cache uploads per-image so multi-group broadcasts upload once. A CDN thumbnail alone is still not sufficient for the banner: a payload with `thumbnailDirectPath` + hashes that reached the message and was fetched by WA from its CDN (confirmed in logs via `[UploadTrace] upload OK` + `media-sea1-1.cdn.whatsapp.net` fetch) still rendered as a compact card until the result object also carried wwebjs's top-level `preview: true` and `subtype: 'url'` flags (set on the result object itself, not `result.data`, at Utils.js ~line 614) — mirror the full result shape, never just `{url, data}`. Confidence: 0.7
- When replicating a library's internal pipeline in a monkey-patch (e.g., wwebjs's in-page media upload), replicate the complete call sequence including intermediate wrapper/precondition steps — never an abbreviated copy. The upload failed with `mediaData.mediaBlob.url is not a function` precisely because the `OpaqueData.createFromData` wrap (performed by wwebjs before calling `.url()`/`.autorelease()`) and the `shouldUseMediaCache` in-memory blob cache step were skipped. Verify each step against the library's actual source (e.g., `node_modules/whatsapp-web.js/src/util/Injected/Utils.js`) rather than approximating from memory. Confidence: 0.85
- WhatsApp's link-preview banner-vs-compact layout is NOT reliably driven by `richPreviewType` alone — the WAProto enum (NONE=0, VIDEO=1, PLACEHOLDER=4, IMAGE=5) is less authoritative than the actual native payload from the live runtime. New evidence overturns the earlier belief that IMAGE=5 is required: the captured WORKING native payload used `richPreviewType: 0` (NONE) and still rendered a full banner via `thumbnailHQ` + `thumbnailDirectPath` + matching hashes. The field must be set to whatever the current native payload in the same log dump carries, never assumed from proto docs or prior iterations. Confidence: 0.6
- WhatsApp CDN thumbnails in link-preview payloads are AES-encrypted and remote (non-sender) devices verify the downloaded CDN blob against the payload hashes — but take the exact hash semantics from the WORKING native payload captured in the same logs, never from assumptions. Fresh evidence from the black-banner fix: the native payload sets `thumbnailSha256 == thumbnailEncSha256` (both = the encrypted CDN blob hash) while our fallback sent a different "plaintext" hash, and that mismatch is what made remote clients render a pitch-black banner; mirroring the native equality is the fix. A payload with `thumbnailDirectPath`/hashes but no `mediaKey` still renders on the sender's Web only. Mirror the native field mapping (`thumbnailSha256`/`thumbnailEncSha256`/`mediaKey`/`mediaKeyTimestamp`) and log plainSha/encSha/mediaKey-presence in the upload trace. Confidence: 0.6
- WhatsApp link-preview fallback payloads must mirror the native payload's full field set, including `thumbnailHQ` (the high-quality base64 JPEG, same bytes as the inline `thumbnail`). Its presence is necessary but NOT sufficient for messages the app composes and sends: WA only auto-uploads `thumbnailHQ` for *received* messages, so a sent preview carrying inline + thumbnailHQ + dims rendered a compact card on all accounts (fresh user report after the thumbnailHQ-only fix deployed) instead of a banner. For sent previews the patch must explicitly call WA's own `WAWebMediaUploadMmsThumbnail` with `OpaqueData.createFromBase64Jpeg(thumbnailHQ)`, `MEDIA_TYPES.NEWSLETTER_THUMBNAIL_LINK`, `forwardedFromWeb: true`, and merge the returned `thumbnailDirectPath` (mediaEntry.directPath) + `thumbnailSha256` (filehash) into the payload — the exact path WA uses for received URL previews (bundle: `refiningTypeIsUrl`). Cache uploads per image and fall back to inline-only on upload failure. Without thumbnailHQ, remote clients are forced to fetch and decrypt the CDN `thumbnailDirectPath` themselves and can fail with a pitch-black banner while the sender's own account renders fine from the inline base64. Diagnostic signature: a fallback payload that works on the sender's account but renders pitch-black (or no image) on other accounts while a sibling link in the same broadcast works — diff the captured fallback object against the captured native object from the same log dump to find the missing or mismatched field (presence AND value parity — e.g., `thumbnailSha256` differing from `thumbnailEncSha256`) rather than re-debugging the CDN upload already proven working. Confidence: 0.7
- WhatsApp link-preview thumbnails for SENT messages must be AES-encrypted CDN entries, not bare unencrypted uploads. Confirmed by log evidence: calling `WAWebMediaUploadMmsThumbnail` with `MEDIA_TYPES.NEWSLETTER_THUMBNAIL_LINK` (the received-preview path) produces an UNENCRYPTED thumbnail entry — WA itself then successfully fetches it from the CDN (`[ReqTrace]` lines showing `media-sea1-1.cdn.whatsapp.net/newsletter-thumbnail-link/...`), yet remote accounts render NO image because a normal-chat client cannot decrypt an unencrypted blob (the upload trace literally reports `mediaKey=MISSING | mediaKeyTs=MISSING` and `thumbnailEncSha256` equals the plaintext `thumbnailSha256`). The confirmed fix is to upload through WA's encrypted pipeline: `WAWebUploadManager.encryptAndUpload({ blob, type: 'image', signal, mediaKey, uploadQpl })` with a self-generated random mediaKey (32 random A-Za-z0-9 chars, mirroring wwebjs's `WWebJS.generateHash`), which returns `uploadedInfo` carrying `directPath` + `encFilehash` + `mediaKey` + `mediaKeyTimestamp` — the same path wwebjs uses for stickers/media (`processStickerData` in `node_modules/whatsapp-web.js/src/util/Injected/Utils.js`). Map into the five native fields as `thumbnailDirectPath` = uploadedInfo.directPath, `thumbnailSha256` = plaintext SHA-256 of the JPEG, `thumbnailEncSha256` = uploadedInfo.encFilehash, plus mediaKey/mediaKeyTimestamp. Diagnostic signature that the CDN layer is done and the encryption layer is the delta: `[PatchTrace] thumbnailHQ uploaded: directPath=...` + `thumbnailHQ=present` + WA fetching the CDN path from `newsletter-thumbnail-link/` + a fully-populated captured payload, but the user still reports "no image link preview from other accounts" — stop re-debugging the upload and diff for mediaKey/thumbnailEncSha256 presence against the native payload instead. Confidence: 0.65
- WhatsApp's native `getLinkPreview` backend crawl is flaky per-URL even within the same site/domain/WAF — in a single 17-article broadcast only 4 articles got `KEEP_NATIVE` (full CDN thumbnail → banner) while 13 got `INJECT_FALLBACK` (`nativeThumbLen=0`), with ASCII and Devanagari image filenames on both sides — so intermittent per-article preview failures are NOT a filename/encoding problem, and the fallback must be robust for every article. When the fallback runs, `WAWebMediaUploadMmsThumbnail` alone yields a payload missing `mediaKey`/`mediaKeyTimestamp`/`thumbnailEncSha256` (receiver: no image or a stale cached one; sender's own client: small card from the inline base64) — instrument the upload with a key-dump log to confirm which fields the bundle actually exposes before committing to a fix. Confidence: 0.7
- When a client's site markup is inconsistent across articles (headings/classes vary — "it can never be just h3 or a specific class"), do not key extraction on a specific tag or class; anchor on structural position instead (e.g., the first text element — p, h1–h6, blockquote, li — after the article image), skip known noise blocks (e.g., `.code-block` ad divs) wedged between the anchor and the content, and fall back to the first text block in the container when the anchor is absent. Accept the client's poor markup as a given ("which is a bad practice on their end but we have to deal with it") and engineer around it rather than demanding clean markup. Confidence: 0.85
- A blanket `page.setRequestInterception(true)` in Puppeteer routes EVERY page request (media uploads, ajax/bz keepalives, service workers) through the CDP interception layer; with the renderer already busy running injected code, that starves the request pipeline and the page stops answering `evaluate()` calls — manifesting as `Runtime.callFunctionOn timed out` on every send at exactly the 180s protocol timeout. Keep interception a near no-op for unrelated traffic: filter by hostname synchronously in the request handler and `continue()` non-relevant requests inline without spawning async work, so WhatsApp's own request stream never touches the CDP matching logic. Confidence: 0.7
